# 1. Introduction

This chapter defines the mandatory engineering rules that every AI coding assistant must follow while contributing to this project.

These instructions are independent of the AI model being used. Whether the code is generated by ChatGPT, Claude, Gemini, Antigravity IDE, GitHub Copilot, Cursor, Windsurf, or another assistant, the generated code must comply with these standards.

Whenever an AI suggestion conflicts with this Project Bible, **the Project Bible takes precedence**.

---

# 2. Primary Objective

The AI assistant must generate code that is:

- Correct
- Readable
- Secure
- Maintainable
- Scalable
- Production-ready
- Consistent with the project's architecture

The AI should prioritize long-term maintainability over short-term convenience.

---

All generated code must respect this architecture.

---

# 4. Core Architecture Rules

These rules are mandatory.

### Rule 1

Never place business logic inside API routes.

Routes should only:

- Receive requests
- Validate input
- Call services
- Return responses

---

### Rule 2

Never access the database directly from API routes.

Database communication must always occur through repositories.

---

### Rule 3

Never call an AI provider directly from API routes.

All AI communication must pass through:

```text
Route

↓

AI Service

↓

Provider Interface

↓

Provider Implementation
```

---

### Rule 4

Never bypass the Service Layer.

Business rules belong exclusively in services.

---

### Rule 5

Every feature should follow the same architecture.

```text
Route

↓

Service

↓

Repository

↓

Database
```

---

### Rule 6

Keep responsibilities separated.

One file.

One responsibility.

---

# 5. Backend Development Rules

The AI must:

- Use FastAPI best practices.
- Use Dependency Injection.
- Create Pydantic schemas.
- Separate request and response models.
- Use SQLAlchemy ORM.
- Use Alembic migrations.
- Keep services reusable.
- Keep repositories database-focused.

Never generate monolithic files.

---

## File Expectations

Authentication feature should include:

```text
api/auth.py

services/auth_service.py

repositories/user_repository.py

schemas/auth.py

models/user.py
```

Do not combine unrelated features.

---

# 6. Frontend Development Rules

The frontend should:

- Use Next.js App Router.
- Use TypeScript.
- Use Tailwind CSS.
- Use shadcn/ui components.
- Keep UI components reusable.
- Keep business logic outside UI components.

API communication should occur through dedicated service files.

Never hardcode backend URLs throughout the project.

---

# 7. Database Rules

The AI must:

- Use SQLAlchemy ORM.
- Create proper relationships.
- Use foreign keys.
- Use indexes where appropriate.
- Use constraints.
- Keep migrations through Alembic.

Never execute raw SQL unless absolutely necessary.

---

# 8. AI Integration Rules

The project supports multiple providers.

Never tightly couple the application to a single provider.

Always use:

```text
AIService

↓

Provider Interface

↓

GeminiProvider

OpenAIProvider

GroqProvider

OpenRouterProvider

OllamaProvider
```

Adding a new provider should require only a new provider implementation.

No changes should be needed in routes or business logic.

---

# 9. Security Rules

The AI must never:

- Hardcode secrets.
- Store API keys in source code.
- Expose passwords.
- Return sensitive database fields.
- Trust frontend validation alone.

Always:

- Validate input.
- Hash passwords.
- Verify JWT tokens.
- Protect private endpoints.
- Read secrets from environment variables.

Security is mandatory.

---

# 10. Code Quality Rules

Generated code should be:

- Readable
- Modular
- Typed
- Reusable
- Well structured

Avoid:

- Deep nesting
- Duplicate logic
- Long functions
- Magic numbers
- Unclear variable names

Prefer explicit code over clever code.

---

# 11. API Design Rules

Every endpoint should:

- Validate requests.
- Return consistent responses.
- Use appropriate HTTP status codes.
- Return meaningful error messages.

Example:

```json
{
    "success": true,
    "message": "User created successfully.",
    "data": {
        ...
    }
}
```

Errors should follow a consistent structure.

---

# 12. Error Handling Rules

The AI should:

- Handle expected exceptions.
- Raise custom exceptions where appropriate.
- Log unexpected failures.
- Return user-friendly error messages.

Do not expose stack traces or internal implementation details.

---

# 13. Testing Rules

When implementing significant functionality, the AI should also suggest or generate:

- Unit tests
- API tests
- Integration tests (where appropriate)

Mock external services such as AI providers to keep tests deterministic.

---

# 14. Documentation Rules

Every major feature should include:

- Clear function names.
- Helpful docstrings where appropriate.
- Updated API documentation.
- Updated Project Bible sections if the architecture changes.

Documentation should evolve with the code.

---

# 15. What AI Must Never Do

The AI must never:

- Write business logic in API routes.
- Mix multiple responsibilities into one file.
- Expose API keys.
- Skip input validation.
- Skip authentication checks on protected routes.
- Duplicate existing functionality.
- Ignore established folder structures.
- Introduce dependencies without justification.
- Change architecture without explicit approval.
- Modify unrelated code to implement a feature.

If uncertain, the AI should ask for clarification rather than making assumptions.

---

# 16. AI Response Guidelines

When asked to generate code, the AI should:

1. Understand the request.
2. Identify where the feature belongs in the architecture.
3. Explain the implementation approach briefly.
4. Generate code that follows project standards.
5. Mention any new files that need to be created.
6. Avoid unnecessary complexity.
7. Keep responses focused on the requested task.

The AI should avoid overengineering while still producing production-quality code.

---

# 17. Definition of Done

A feature is considered complete only when:

- Architecture rules are followed.
- Code compiles successfully.
- Validation is implemented.
- Error handling is included.
- Security considerations are addressed.
- Database changes have migrations.
- API responses are consistent.
- Documentation is updated if necessary.
- Tests are added or existing tests are updated.

Code that only "works" but violates project standards is **not** considered complete.

---

# 18. Chapter Summary

This chapter established the engineering contract between the project and any AI coding assistant.

By following these instructions, AI-generated code remains consistent with the project's architecture, coding standards, and long-term goals. The rules defined here ensure that every contribution—regardless of the AI model used—supports a clean, modular, secure, and scalable codebase.

As AI-assisted development becomes a larger part of software engineering, maintaining a clear set of project-specific instructions is essential for preserving architectural integrity and minimizing technical debt.

---

## AI Assistant Checklist

Before generating code, verify the following:

- [ ] Does the solution follow the defined architecture?
- [ ] Is business logic placed in the Service Layer?
- [ ] Is database access limited to repositories?
- [ ] Is AI communication routed through the AI Service?
- [ ] Are request and response schemas defined?
- [ ] Is input validation implemented?
- [ ] Are environment variables used for secrets?
- [ ] Is the code modular and reusable?
- [ ] Does the implementation avoid duplication?
- [ ] Are errors handled gracefully?
- [ ] Are naming conventions followed?
- [ ] Is documentation updated if the architecture changes?

Only when every applicable item is satisfied should the implementation be considered complete.
